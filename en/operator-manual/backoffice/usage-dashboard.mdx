## Overview

Open **Backoffice > Platform > AI Usage** to understand AI consumption across your gateways, API keys, and Workspace activity. Use the dashboard to identify high consumers, compare request activity over time, and investigate a selected day or consumer.

Access requires **Operator** or **Super Admin** permissions. [Audit Log](/en/operator-manual/configuration/features/feat-audit) logging and storage must be enabled. To inspect individual requests, also enable the Activity Registry feature and use [Activity explorer](/en/operator-manual/backoffice/activity-registry).

## Summary and charts

The four summary cards show **Recorded chat tokens**, **Chat requests**, **Attributed users**, and **Requests completed** for the selected scope. Tokens include available input and output values. Requests completed means requests without a recorded error.

| Chart | What it shows |
| --- | --- |
| **Token consumption over time** | Daily recorded input and output tokens, shown separately. The coverage note identifies requests with both token values recorded. |
| **Requests over time** | Daily requests split by recorded success or error. |
| **Active users over time** | Distinct attributed users per day. These daily counts are not additive across days. |
| **Response performance** | Daily average response latency and time to first response block. Requests without recorded timings are excluded. |
| **Tokens by API key** | Top API keys by recorded chat tokens. |
| **Token consumption concentration** | The top five user consumers and the remaining recorded consumption, grouped as **Others**. |
| **Most active users** | Top users by request count in the selected scope. |
| **Files ingested**, **File searches**, **Embeddings** | Additional daily ingestion, file-search, and embedding activity when available. |
| **Tools recorded** | Recorded calls by tool, including knowledge search, web search, code execution, database queries, document creation, and web extraction. |

A recorded tool call does not prove that the tool ran successfully. Missing tool records can also mean that logging was disabled. Additional usage charts show an unavailable state when their data is absent.

### Consumer rankings

**Who consumes the most** lists consumers by recorded tokens. Switch between **Users** and **API keys** to compare token totals, request counts, tokens per request, and each consumer's share of usage.

The table initially shows the top 10 consumers. Use **Show all** to display the available ranking and **Show top 10** to collapse it. A notice appears when the returned ranking is limited; expanding the table does not remove that limit.

## Filters

Usage and Activity explorer share the same filters. Filter state is stored in the URL, so you can refresh or share a view with another authorized Backoffice user.

<Tabs>
  <Tab title="Gateway">
Select **All gateways** or one or more gateways.

Changing the gateway selection keeps compatible API-key selections and removes keys outside the new scope. It also resets **Attributed user** to **All users**.
  </Tab>
  <Tab title="API key">
Select **All API keys**, one or more keys, or **Non API Users** to include records without an API key.

**All API keys** includes both API-key activity and activity without a recorded key, such as Workspace requests. Selecting a specific key excludes requests without that key. Changing the key selection resets **Attributed user** and can adjust the gateway scope to match the selected keys.
  </Tab>
  <Tab title="Attributed user">
Select **All users**, one or more recorded identities, or **Unattributed** for requests without a recorded account identity.

The available users follow the gateway, API-key, status, and date scope. When the user list reaches its limit of 1,000, narrow those filters to find more users.
  </Tab>
  <Tab title="Status">
Select **All statuses**, **Success**, or **Error**. Status comes from the recorded request outcome: Success means no error was recorded.

Changing status resets **Attributed user** to **All users**.
  </Tab>
  <Tab title="Date range">
The default is **Last 30 days**. Available presets are **Week to date**, **Month to date**, **Last 7 days**, **Last 14 days**, and **Last 30 days**.

You can select a custom range. Future dates and dates before **January 1, 2026** are unavailable. Reversed dates are normalized. A range longer than **90 days** is shortened to the last 90 days ending on the selected end date.

Changing dates resets **Attributed user** to **All users**.
  </Tab>
</Tabs>

**Reset filters** restores all gateways, API keys, users, and statuses, with the last 30 days. Changing filters resets the Activity explorer to its first page. The former **Group by**, **Show**, and **Keys** controls have been replaced by these filters.

## Open a report

1. Use **Expand report** on a supported chart to open its larger chart and breakdown table.
2. Select a chart day, a request status within a day, or a user/API-key consumer to inspect that narrower scope.
3. Review the selected dates and filter badges in the report. Consumer reports show consumption and request performance for that identity or key.
4. When Activity Registry is enabled, use **View requests** to open Activity explorer with the report's filters. This action is not offered for tool reports.

## Attribution and limitations

- Workspace requests use sessions rather than API keys. They contribute to gateway totals and can appear under **Non API Users**. A missing key alone does not identify the request's origin.
- API requests are attributed to the key owner; the person using an application may be different. Requests without an account identity remain **Unattributed** and are included in totals.
- When names are unavailable, the dashboard uses recorded email addresses or IDs. A notice explains partial failures loading filter names; available metrics remain usable.
- Missing token values and timings are not the same as recorded zeroes. Totals include available token values; timing averages exclude missing timings.
- No matching requests produces an empty state. Failed dashboard or report loads offer a retry control.
- Usage and reports are read-only and have no export or download controls. There are no organization or project filters.
- Metrics depend on retained log data. [Hard Delete](/en/operator-manual/configuration/cron-tasks/hard-delete) and retention policies can remove records from the available history. Keep deployment clocks synchronized.
