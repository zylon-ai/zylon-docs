Messages is the core of ZylonGPT. You send a conversation history, and Zylon returns the next assistant message as a **list of content blocks** (text, tool calls, tool results, and more).

## Prerequisites

- An API token. See [Backoffice Developer Console](/en/developer-manual/get-started/developer-console).
- Your Zylon hostname (replace `{BASE_URL}` in the examples).

`PrivateGPT.Read.All` permits synchronous `POST /messages`, `POST /messages/validate`, and the other endpoints in the [ZylonGPT read-only allowlist](/en/developer-manual/build-with-zylon/zylon-gpt-api/overview). `Read.All` permits the same calls only when the account token carries `gateway_id`; without gateway context, it cannot call ZylonGPT. Effective access also depends on the token owner's role permissions.

## Basic request and response

Send one user message and get back one assistant message.

<Tabs>
  <Tab title="Single message">
```bash
curl -X POST "https://{BASE_URL}/api/gpt/v1/messages" \
  -H "Authorization: Bearer {API_TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "default",
    "max_tokens": 32,
    "temperature": 0,
    "messages": [
      { "role": "user", "content": "Write a one-sentence status update about deploying a billing dashboard and fixing three bugs." }
    ]
  }'
```
  </Tab>

  <Tab title="Content blocks">
```bash
curl -X POST "https://{BASE_URL}/api/gpt/v1/messages" \
  -H "Authorization: Bearer {API_TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "default",
    "max_tokens": 32,
    "temperature": 0,
    "messages": [
      {
        "role": "user",
        "content": [
          { "type": "text", "text": "Write a one-sentence status update about deploying a billing dashboard and fixing three bugs." }
        ]
      }
    ]
  }'
```
  </Tab>
</Tabs>

## Messages shape

The same message body is used by ZylonGPT and by the `pgpt` field in Workspace chat/interaction requests. Send conversation content; the selected model or gateway determines which optional settings it supports. `model` and `max_tokens` are nullable options, rather than universally required fields. Keeping them explicit makes model selection and output limits predictable; validate requests against your gateway.

<Accordion title="Request body">

| Field | Type / default | Description |
| --- | --- | --- |
| `messages` | message[]; `[]` | Conversation history. Each message has `role` (`user` or `assistant`) and `content` (string or content-block array). Workspace interaction creation requires exactly one user message. |
| `model` | string or null | Model name, commonly `default`; validate omission against the selected gateway. |
| `max_tokens` | integer or null | Output token limit, subject to model validation. |
| `stream` | boolean; `false` | ZylonGPT Messages returns JSON by default and SSE when `true`. Current `/app/chat` and Workspace interaction routes stream regardless of this flag. |
| `system` | string, object, object[], or null | System text and configuration; nested fields below. |
| `tools` | object[] or null | Tool definitions. See [Tools](/en/developer-manual/build-with-zylon/tools/introduction-to-tools). |
| `tool_choice` | object or null | Tool selection and validation settings below. |
| `tool_context` | object[] or null | Typed context, such as `ingested_artifact` or `sql_database`; see the relevant tool guide. |
| `mcp_servers` | object[] or null | MCP server configurations. Each requires `url`; `name` and `tool_configuration` are optional. |
| `thinking` | object or null | `enabled` defaults to `false`; `type` (string) and `budget_tokens` (integer) are optional. |
| `output_config` | object or null | `effort`: `low`, `medium`, `high`, or `max`; optional `format` described below. |
| `cache_control` | object or null | When supplied, requires string `type`. Support depends on the model. |
| `temperature`, `min_p`, `top_p` | number or null | Sampling options; supported ranges depend on the model. |
| `top_k` | integer or null | Sampling option. |
| `repetition_penalty`, `presence_penalty`, `frequency_penalty` | number or null | Token penalty options. |
| `seed` | integer or null | Optional sampling seed. |
| `priority` | integer or null | Optional request priority. |
| `stop_sequences` | string[]; `[]` | Custom generation boundaries. |
| `metadata` | object; `{}` | Optional nullable string `ws_member_id`. Use a workspace-member ID, not an account ID. `user_id` remains an input alias; send only one name. |
| `service_tier` | string; `auto` | `auto` or `standard_only`. |
| `inference_geo` | string or null | Optional inference location preference. |
| `container` | string or null | Optional existing container identifier. |
| `message_id`, `correlation_id` | string or null | Optional message and correlation identifiers. |

Nullable fields can be omitted. A non-nullable option with a default can be omitted but should not be sent as `null`.

</Accordion>

<Accordion title="System, tool choice, and structured output">

| Object | Field | Type / default |
| --- | --- | --- |
| `system` | `text` | Optional string. |
| `system` | `citations` | Object; `enabled` defaults to `false`, `known_citations` is an optional citation array. |
| `system` | `blob_visibility` | Optional `binary`, `internal`, or `public`. |
| `system` | `extensions` | Optional string[]; currently supports `zylon`. |
| `system` | `prompt` | Object with boolean `tools`, `citations`, `thinking`, `code_execution`, and `skills`; each defaults to `false`. |
| `tool_choice` | `type` | String; `auto`. |
| `tool_choice` | `name` | Optional string identifying a tool. |
| `tool_choice` | `disable_parallel_tool_use` | Boolean; `false`. |
| `tool_choice` | `validation_mode` | `eager` or `lazy`; `lazy`. |
| `output_config.format` | `type` | Required `json_schema`. |
| `output_config.format` | `schema` | Required JSON Schema object. |

`response_format` is deprecated; use `output_config.format`. Move deprecated `thinking.effort` to `output_config.effort`. Replace `system.use_default_prompt` with the individual `system.prompt` flags; setting the old flag to `true` enables all prompt categories.

</Accordion>

<Accordion title="Message response fields">

| Field | Type | Meaning |
| --- | --- | --- |
| `id`, `type`, `role`, `model` | string | Message identity, `message` type, `assistant` role, and selected model. |
| `created` | integer | Epoch milliseconds. |
| `content` | object[] | Content blocks. See the [1.58 server tool blocks](/en/developer-manual/build-with-zylon/workspace-api/api-migration-1-57-to-1-58#server-tool-content-blocks). |
| `stop_reason` | string or null | `end_turn`, `max_tokens`, `stop_sequence`, `tool_use`, `pause_turn`, or `refusal`. |
| `interaction_stop_reason` | string or null | Overall interaction outcome: `stop`, `error`, `cancelled`, or `refusal`. |
| `stop_details` | object or null | Required `type`, optional `category` and `explanation`. |
| `container` | object or null | Required `id`, optional `expires_at` string. |
| `usage` | object | `input_tokens` and `output_tokens` (default `0`); optional cache and server-tool usage below. |
| `errors` | object[] | Error details when available. |

`usage` may include `cache_creation_input_tokens`, `cache_read_input_tokens`, `inference_geo`, `service_tier`, `cache_creation` (`ephemeral_1m_input_tokens`, `ephemeral_1h_input_tokens`, `ephemeral_5m_input_tokens`), and `server_tool_use` (`web_fetch_requests`, `web_search_requests`). Counts in the nested usage objects default to `0`. Nullable response fields may be omitted. There is no top-level `stop_sequence` field; use `stop_reason: "stop_sequence"`. See [Handling stop reasons](/en/developer-manual/build-with-zylon/zylon-gpt-api/handling-stop-reasons).

</Accordion>

## Validate a request

Use `/messages/validate` to check payload shape before sending a real request. It returns `valid: true` or a list of validation errors.

```bash
curl -X POST "https://{BASE_URL}/api/gpt/v1/messages/validate" \
  -H "Authorization: Bearer {API_TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "default",
    "max_tokens": 32,
    "messages": [
      { "role": "user", "content": "Validate this payload." }
    ]
  }'
```

Example response:

```json
{ "valid": true, "errors": null }
```

## Multi-turn conversations

To continue a conversation, include the prior turns in `messages`:

```bash
curl -X POST "https://{BASE_URL}/api/gpt/v1/messages" \
  -H "Authorization: Bearer {API_TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "default",
    "max_tokens": 16,
    "temperature": 0,
    "messages": [
      { "role": "user", "content": "My name is Ada." },
      { "role": "assistant", "content": "Nice to meet you." },
      { "role": "user", "content": "What is my name? Reply with only the name, no punctuation." }
    ]
  }'
```

## System prompts

Use the top-level `system` field to control assistant behavior (instead of a `"system"` role message):

{/* <!-- ADDED FOR CLARITY --> */}
<Callout type="tip">
  Prefer the top-level <code>system</code> field for system instructions so they are applied consistently across the whole request.

```bash
curl -X POST "https://{BASE_URL}/api/gpt/v1/messages" \
  -H "Authorization: Bearer {API_TOKEN}" \
  -H "Content-Type: application/json" \

    "model": "default",
    "max_tokens": 8,
```

## Structured JSON output (json_schema)

If you need machine-readable output, set `output_config.format.type` to `json_schema` and provide `output_config.format.schema`. Zylon returns JSON as text in a `text` content block.

```bash
curl -X POST "https://{BASE_URL}/api/gpt/v1/messages" \
  -H "Authorization: Bearer {API_TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "default",
    "max_tokens": 128,
    "system": {
      "text": "Return ONLY valid JSON."
    },
    "messages": [
      {
        "role": "user",
        "content": "We deployed the billing dashboard. Return a status and the next step."
      }
    ],
    "output_config": {
      "format": {
        "type": "json_schema",
        "schema": {
          "type": "object",
          "additionalProperties": false,
          "properties": {
            "status": {
              "type": "string"
            },
            "next_step": {
              "type": "string"
            }
          },
          "required": [
            "status",
            "next_step"
          ]
        }
      }
    }
  }'
```

## Streaming (SSE)

Set `stream: true` to receive a `text/event-stream` response containing events like `content_block_delta` (token deltas).

```bash
curl -N -X POST "https://{BASE_URL}/api/gpt/v1/messages" \
  -H "Authorization: Bearer {API_TOKEN}" \
  -H "Content-Type: application/json" \
  -H "Accept: text/event-stream" \
  -d '{
    "model": "default",
    "stream": true,
    "max_tokens": 32,
    "messages": [
      { "role": "user", "content": "Give a three-word tagline for a productivity app." }
    ]
  }'
```

## Async messages

<Warning>
Async message start, stream, status, cancel, and delete routes require `PrivateGPT.ReadWrite.All` or `ReadWrite.All`. Read-only tokens receive `403` for every async lifecycle route.
</Warning>

Async messages use the **same request body** as sync messages—you just call a different endpoint. The main difference is the **response shape**: sync returns a full message, async returns a `message_id` you can stream or poll later.

### Start an async message

```bash
curl -X POST "https://{BASE_URL}/api/gpt/v1/messages/async" \
  -H "Authorization: Bearer {API_TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "default",
    "max_tokens": 32,
    "messages": [
      { "role": "user", "content": "Say only: async ok" }
    ]
  }'
```

### Stream or poll status

Stream events:

```bash
curl -N "https://{BASE_URL}/api/gpt/v1/messages/async/{message_id}/stream" \
  -H "Authorization: Bearer {API_TOKEN}" \
  -H "Accept: text/event-stream"
```

Poll status:

```bash
curl "https://{BASE_URL}/api/gpt/v1/messages/async/{message_id}/status" \
  -H "Authorization: Bearer {API_TOKEN}"
```

### Cancel or delete

- Cancel: `POST /messages/async/{message_id}/cancel`
- Delete: `DELETE /messages/async/{message_id}/delete`

## Common mistakes

- **Wrong method**: `/messages` is `POST`, not `GET`.
- **Missing auth header**: include `Authorization: Bearer ...`.
- **Wrong base URL**: use `https://{BASE_URL}/api/gpt/v1/`.
- **Invalid request body**: use `POST /messages/validate` to catch schema mistakes early.
- **Unexpected stops or errors**: see [Handling stop reasons](/en/developer-manual/build-with-zylon/zylon-gpt-api/handling-stop-reasons) for causes and fixes.
