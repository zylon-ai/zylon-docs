---
title: "Make tasks easier for smaller models"
description: "Reduce unnecessary decisions and evaluate the results on your own projects."
noindex: true
---

A smaller model can be a useful choice for local execution, latency or resource constraints. Model size alone does not tell you whether it can complete your task: tool support, training, provider behavior and the project all matter. Choose a [compatible model](/zylon-code/models/choosing-a-model), then evaluate it on representative work.

The following practices are starting points to test. They do not guarantee success or make a smaller model equivalent to a more capable one.

## Reduce what the model must infer

Give one concrete outcome, relevant source files, an existing pattern and a check. In the search example:

> Update the existing filtering function so empty and whitespace-only queries return all items in their current order. Keep non-empty matching unchanged. Follow the existing test style, add the missing cases and run the focused command documented in AGENTS.md.

This is easier to assess than “make search better”. If the task is still too broad, separate investigation, implementation and review into clear steps, preserving decisions between them.

Use an existing neighboring implementation as an example when it is relevant. Explain what should be followed—error handling, return type or test organization—rather than asking the agent to copy the whole file. Wrong examples can guide the model toward the wrong behavior.

## Keep instructions short and consistent

Give the applicable rules at the time they are needed. Avoid a long prompt full of speculative exceptions and repeated warnings. Ask for the next observable action and its result, not an enormous plan for all possible outcomes.

For a report, a simple format can make omissions visible:

```text
Result: implemented / blocked
Changed files:
Checks actually run and their results:
Requirements not yet verified:
Next action, if any:
```

Structured output helps you read the report; it does not make the contents true. Verify the listed commands and the actual diff. Do not require the agent to expose private internal reasoning: concise explanations of decisions and evidence are sufficient.

## Use only the tools the task needs

Start with an appropriate [mode](/zylon-code/modes/overview). If the model struggles with a large tool catalog, try a narrower [custom mode](/zylon-code/customization/custom-modes) while retaining the capabilities needed to finish. Start a new conversation with that mode and bring the task handoff; changing the default does not reconfigure an existing conversation. Tool-call compatibility matters: a model that writes tool names as prose has not executed those tools.

Keep feedback specific. Return the failing assertion and the relevant error instead of asking the agent to reinterpret a massive log. For longer work, split it into independently checkable outcomes and keep a [handoff](/zylon-code/hardening/session-state) between them.

## Escalate when the task exceeds the model

If tool calls remain invalid, architectural decisions remain inconsistent or the same defect survives focused correction attempts, change the approach. Supply missing facts, choose another compatible model or involve a person. Adding more instructions or agents is not always the answer.

Compare the same tasks under the same checks before deciding a change helped. Include failures, rework and your review time; a fast response is not necessarily a completed task.

Continue with [delegation and independent review](/zylon-code/hardening/agents-and-review).

Further reading: [Anthropic's Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) on simple workflows and clear tools; [Lost in the Middle](https://arxiv.org/abs/2307.03172) on limitations of long-context use. These sources motivate practices to evaluate, not a fixed recipe for every model.
