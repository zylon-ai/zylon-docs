Edit the provider in **Settings → Models** and open its customized model settings. These values describe the endpoint; they do not increase its actual capacity.

| Option | What to enter |
| --- | --- |
| Model ID | Exact API identifier accepted by the endpoint. |
| Display name | A recognizable label for the picker. |
| Context window | The model’s supported token capacity for a request. |
| Maximum output | The model's supported output capacity. |
| Request output limit | Default output budget for an ordinary request; separate from the model's capacity. |
| Input types | Text and/or image only when the model supports them. |

## Capacity and request budget

For example, a deployment may support a 131,072-token context and 32,768 output tokens while reserving 8,192 for an ordinary reply. Enter the server-supported capacities and choose a request limit no larger than its output capacity. These example numbers are not performance recommendations.

Newly discovered Zylon models default to a request limit of 8,192 tokens, or their lower advertised output capacity. Refresh preserves existing model fields and manual rows; it does not replace old limits with new discovery values. Review existing rows explicitly after a server change.

A large output reservation leaves less room for input. The summary used for [compaction](/zylon-code/everyday-use/long-conversations) has a separate budget; reducing the normal reply limit does not automatically reduce that summary limit. Ask your administrator to align compaction with a small model's capacity.

## Images

Expand the model's options and select **Image** if supported. At least one input type must remain selected. New custom models without inherited image capability begin as text-only. Screenshot-based tools need an image-capable model; the server must also support sending those images.

## Reasoning capabilities

Reasoning controls come from the selected model's advertised capabilities. Zylon models that report support offer **Off** and their supported effort levels in the composer. Use **Refresh models** to add newly available models. Refresh preserves saved reasoning declarations too; ask your administrator to update an existing model's declarations when its capabilities change. Without configured reasoning capabilities, the Effort control is absent.

Use [Choose a model](/zylon-code/models/choosing-a-model) for the steps to enable, disable or change effort. Selecting another model applies that model's default. Editing a model's configured default does not replace an effort already selected in a conversation. **Default**, when offered, sends no explicit reasoning choice for Zylon.

The gateway's model adapter ultimately decides how the requested level is used. Some adapters map Off to a low level or Max to High when the underlying model cannot honor the exact setting. Ask your administrator about the behavior of your deployment if that distinction matters to a task.

## Defaults and errors

Inherited catalog values and saved overrides are different. Restoring a whole provider catalog can remove other edits too; review the form before resetting it. A wrong model ID or protocol can save successfully and still fail during inference.

For adapter-only options such as headers, request compatibility, retries and timeouts, use [profiles and YAML](/zylon-code/advanced/profiles-and-yaml) with the installed configuration schema. Keep keys out of YAML literals.
