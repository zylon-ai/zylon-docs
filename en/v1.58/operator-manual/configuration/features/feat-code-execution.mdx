<Note>**Feature in Beta**</Note>

Code execution lets the assistant run bash commands and create, edit, and present files inside an isolated sandbox. Each chat thread (or API `container`) gets its own sandbox, created on demand by the bundled OpenSandbox service on the same Kubernetes cluster.

Users see it in the Workspace when they work with Skills or generate files. Developers can use it through the API; see [Code Execution tool](/en/v1.58/developer-manual/build-with-zylon/tools/built-in/code-execution-tool).

Code execution is **enabled by default in standard Zylon 1.58 deployments**. Operators can control its availability in Workspace chat with the setting below.

### Configuration

| Key | Default | Values | Description |
|-----|---------|--------|-------------|
| `features.codeExecution.enabled` | `true` | `true \| false` | Allow code-execution tools in Workspace chat; see [When disabled](#when-disabled) for API limitations |
| `features.codeExecution.timeout` | `60` | seconds | Default timeout for each command run in the sandbox |
| `external.opensandbox.sessionTTLSeconds` | `600` | seconds | How long an idle sandbox is kept running before it's shut down. Files are kept; the next request starts a new sandbox with the same files. |

### Example

```yaml
features:
    codeExecution:
        enabled: true
        timeout: 60
```

To disable code-execution tools in Workspace chat:

```yaml
features:
    codeExecution:
        enabled: false
```

### When disabled

After setting `features.codeExecution.enabled: false`, run `sudo zylon-cli sync` to apply the change. Workspace chat removes code-execution tools before sending requests to the model, including when a Skill would otherwise add them. Ordinary chat and other available tools continue to work; Skill steps that require running code cannot execute through that chat flow.

<Warning>
In Zylon 1.58, this flag **does not globally disable code execution through the ZylonGPT API** or remove the OpenSandbox service. The GPT provider is configured separately and defaults to OpenSandbox. Treat this flag as a Workspace control; API code execution can remain available.
</Warning>

### How it works

- **One sandbox per thread.** Each sandbox is a pod in the `opensandbox-runtimes` namespace, created when the assistant first runs code in a thread and shut down after `sessionTTLSeconds` of inactivity.
- **Persistent files.** Uploads, outputs, and workspace files are stored in the `sessions` bucket of the platform object storage, so they survive sandbox restarts and platform upgrades.
- **Pre-pulled images.** The sandbox images are pulled during installation and upgrade, so no registry access is needed when a sandbox starts. This also works in airgapped installations.

### Network access

Sandboxes have no internet access. By default, a code execution sandbox can only reach:

- DNS.
- The Zylon API, so code in the sandbox can call the model with the permissions of the user who sent the request.

To let sandboxes reach other services inside the cluster, such as an internal database or API, add them to `external.opensandbox.codeExecution.internal.services`. Each entry selects pods by their labels: `namespaceSelector` takes the namespace's labels and `podSelector` the pods' labels. List the labels directly, without `matchLabels` (Zylon adds it), and give each selector at least one label: an empty one would let sandboxes reach every pod in the cluster.

```yaml
external:
    opensandbox:
        codeExecution:
            internal:
                services:
                    - namespaceSelector:
                          kubernetes.io/metadata.name: analytics
                      podSelector:
                          app: postgres
```

<Warning>
Code in the sandbox is written by the AI model. Only allow services that you're comfortable exposing to any user who can chat with the assistant.
</Warning>

### Resources

By default, sandboxes don't have CPU or memory limits. To cap the total resources sandboxes can use, enable the quota and limit range for the sandbox namespace:

```yaml
opensandbox:
    runtime:
        resourceQuota:
            enabled: true    # Total for all sandboxes: 50 pods, 20 CPU, 40Gi memory (limits)
        limitRange:
            enabled: true    # Per sandbox: 1 CPU, 512Mi memory by default
```

### Sandbox images

| Key | Default |
|-----|---------|
| `external.opensandbox.codeExecution.image.repository` | `zylon-sandbox-templates/code-execution` |
| `external.opensandbox.codeExecution.image.tag` | `1.1.0` |

The image includes Python 3 with common data libraries (pandas, numpy, matplotlib, openpyxl, python-docx, pypdf, and others) and command-line tools such as `unzip`, `rg`, and `sqlite3`.

### Troubleshooting

Check the sandboxes that are running:

```bash
sudo kubectl get pods -n opensandbox-runtimes
```

Check the OpenSandbox server logs:

```bash
sudo kubectl logs -n opensandbox deploy/opensandbox-server --tail=200
```

If code execution is unavailable in Workspace chat, check `features.codeExecution.enabled` and run `sudo zylon-cli sync` after changing it.

The error `code_execution provider is not configured.` means the GPT code-execution provider is missing. Check the GPT provider configuration and OpenSandbox service; this error is not the expected result of disabling the Workspace flag alone.
