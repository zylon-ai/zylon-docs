---
title: "Logging"
description: "Retrieve Zylon platform logs manually from the Backoffice API."
---

The Backoffice Logging endpoints let authorized Backoffice users retrieve stored Zylon logs for investigation, review, export, or integration jobs.

This page covers manual retrieval only. For external syslog or HTTP delivery, see [Log Delivery and Storage configuration](/en/operator-manual/configuration/features/log-delivery-storage).

These endpoints are read-only. The documented API exposes `GET` operations for listing stored logs and usage data; it does not expose per-record update, patch, or delete operations.

## Prerequisites

| Requirement | Value |
| --- | --- |
| Authentication | Account token or account session |
| Role | At least the `operator` role |

```bash
curl "https://{BASE_URL}/v1/platform/logs?page=0&page_size=50" \
  -H "Authorization: Bearer {API_TOKEN}"
```

<Note>Workspace-only tokens are not enough for these endpoints.</Note>

For operator-facing guidance on governance, evidence preservation, and SIEM delivery, see [Auditability & AI Governance: Logging, Evidence, and SIEM Delivery](/en/operator-manual/backoffice/log-delivery-storage).

## Endpoints

| Endpoint | Purpose |
| --- | --- |
| `GET /v1/platform/logs` | List stored platform logs across gateway, workspace, security, and backoffice event families. |
| `GET /v1/platform/gateway/{gatewayId}/logs` | List stored logs for one gateway. |
| `GET /v1/platform/logs/{logId}` | Retrieve one retained log with optional recorded details. |
| `GET /v1/platform/usage` | Return aggregate chat usage, rankings, daily operations, and scoped user options. |

## Pagination

The two log list endpoints return a page envelope. Cursor and total-count fields are omitted when unavailable:

<Accordion title="Page envelope">
```json
{
  "data": [],
  "has_next_page": false,
  "has_previous_page": false
}
```
</Accordion>

Supported page parameters:

| Parameter | Description |
| --- | --- |
| `page` | Zero-based absolute page index. Cannot be combined with cursor pagination. |
| `page_size` | Absolute page size. Default is `50`. |
| `page_order` | ID tie-breaker order used by pagination. |
| `after` | Cursor for forward pagination. |
| `before` | Cursor for backward pagination. |
| `first` | Forward cursor page size. Default is `50`. |
| `last` | Backward cursor page size. |
| `total_count` | Set to `true` to include `total_count`. |

Logs are ordered by `start_timestamp` descending. The backend adds log ID ordering as a stable tie-breaker.

## Shared log filters

`GET /v1/platform/logs` and `GET /v1/platform/gateway/{gatewayId}/logs` support these query parameters:

<Accordion title="Endpoint parameters">
All query parameters below are optional.

| Parameter | Type | Description |
| --- | --- | --- |
| `gateway_id` or `gatewayId` | String list | One or more gateway IDs. On the gateway route, the path gateway overrides this selection. |
| `token_id` or `tokenId` | String list | API token IDs, `none` for records without a key, or a mixture of both. |
| `account_id` or `accountId` | String list | Account IDs, `none` for unattributed records, or a mixture of both. |
| `has_error` | Boolean | `true` selects recorded errors; `false` selects records with no error. Omit to include both. |
| `event` | String | One event family from the table below. |
| `action` | String | One serialized action, such as `ws.project.create` or `security.auth.invalid_token`. |
| `organizationId` | String | Match one organization. |
| `projectId` | String | Match project-linked workspace or security logs. |
| `start_date` | Integer | Unix epoch milliseconds; log start must be at or after this value. |
| `end_date` | Integer | Unix epoch milliseconds; log end must be at or before this value. |
| `include` | String | Case-sensitive comma-separated values: `InputPayload`, `Payload`, `Data`, `ChatRequestParameters`, `ChatRequestMessages`, `ChatResponse`. |
</Accordion>

For gateway, token, and account selections, comma-separated values and repeated parameters are combined, trimmed, and deduplicated. Each selection accepts at most 100 distinct values. An omitted selection is unrestricted; an explicitly empty token/account selection is rejected. `none` is supported only for tokens and accounts, and counts toward the limit. Values within a selection are combined with OR; different filters are combined with AND.

The legacy `status=success` and `status=error` values are aliases for `has_error=false` and `has_error=true`; `has_error` takes precedence when both are present. Unlike Usage, log-list date filters have no default reporting window or 90-day cap.

<Note>
Without `include`, `input_payload`, `payload`, and structured `data` are omitted. Empty payload objects are also omitted when requested. Use `include=Data` for structured per-event data. Chat content requires both `Data` and the corresponding chat-specific include value; for example, `include=Data,ChatRequestMessages`.
</Note>

<Note>
The `include` parameter controls retrieval shape only. It does not enable or disable collection. If request messages or responses are present in stored chat logs, they are returned only when the caller requests the corresponding include value.
</Note>

<Warning>
Retrieving very large chat logs can take time, especially when the requested scope is large or when messages and responses are included.
</Warning>

## Log record schema

List entries and the single-log endpoint use the same log record shape. Nullable context and error fields are omitted when absent. Recorded JSON objects can still contain their own null values.

| Field | Notes |
| --- | --- |
| `id` | Log ID. |
| `gateway_id` | Gateway context when available. |
| `system_event` | Whether the backend marked the event as system-originated. |
| `request_id` | Request or generated correlation ID. |
| `event` | Event family. |
| `action` | Action name when available. |
| `organization_id` | Organization context when available. |
| `ws_member_id` | Workspace member context when available. |
| `account_id`, `account_email` | Account context when available. |
| `token_id` | API token context when available. |
| `start_timestamp`, `end_timestamp` | ISO timestamps. |
| `ip_address` | Source IP when available. |
| `metadata` | Additional backend metadata. |
| `input_payload`, `payload` | Included only when requested. Sensitive request keys are masked before storage. |
| `error` | Error message or class name when logged. |
| `data` | Included only with `include=Data`; shape depends on `event`. |

Structured `data` can include workspace, HTTP, security, chat, embed, or ingest fields. Chat data can include model, token counts, request metadata, optional request messages, optional response, latency metrics, and `tools_used`.

Sensitive request keys such as passwords, tokens, API keys, secrets, credentials, cookies, and connection strings are masked before request input payloads are stored. Do not build export workflows that require recovering masked values from logs.

## List platform logs

```http
GET /v1/platform/logs
```

Retrieves stored logs across gateway, workspace, backoffice, and security event families.

```bash

  -H "Authorization: Bearer {API_TOKEN}"
```

## List gateway logs

```http
GET /v1/platform/gateway/{gatewayId}/logs
```

Retrieves stored logs for one gateway. The `{gatewayId}` path parameter is applied by the backend and overrides any `gatewayId` query parameter.

| Path parameter | Description |
| --- | --- |
| `gatewayId` | Gateway whose logs should be returned. |

### Example request

```bash
curl "https://{BASE_URL}/v1/platform/gateway/{GATEWAY_ID}/logs?event=zylon.gateway.chat&tokenId={TOKEN_ID}&first=25&include=Data,ChatRequestMessages,ChatResponse" \
  -H "Authorization: Bearer {API_TOKEN}"
```

## Retrieve one log

```http
GET /v1/platform/logs/{logId}
```

Returns one retained log record, with the same Backoffice permission check and include behavior as the list endpoints. This API can retrieve any supported event family; the Activity explorer UI specifically lists chat requests.

<Accordion title="Endpoint parameters">
| Type | Name | Required | Notes |
| --- | --- | --- | --- |
| Path | `logId` | Yes | ID of the retained log. |
| Query | `include` | No | Same case-sensitive include values as the log lists. Omit for metadata only. |
</Accordion>

```bash
curl "https://{BASE_URL}/v1/platform/logs/{LOG_ID}?include=Data,ChatRequestParameters,ChatRequestMessages,ChatResponse" \
  -H "Authorization: Bearer {API_TOKEN}"
```

The `200` response is one log object, without a page envelope. An invalid log ID or include value returns `400`; a valid ID with no retained record returns `404`.

### Recorded chat details

With `include=Data`, chat records include this structured data when it was stored:

| Field | Type | Notes |
| --- | --- | --- |
| `type` | String | `chat`. |
| `id` | String | Chat log ID. |
| `model` | String | Recorded model identifier. |
| `request_length`, `request_tokens` | Integer | Recorded input length and token count. |
| `response_length`, `response_tokens` | Integer, nullable | Recorded output length and token count. |
| `model_latency`, `response_latency`, `response_ttf` | Number, nullable | Model latency, response latency, and time to first response block, in seconds. |
| `response_tps` | Number, nullable | Recorded output tokens per second. |
| `tools_used` | String array | Recorded tool names; repeated calls can repeat a name. Does not establish successful execution. |
| `request_parameters` | Object, nullable | Stored configuration, only with `Data,ChatRequestParameters`. |
| `request_messages` | Object, nullable | Stored messages, only with `Data,ChatRequestMessages`. |
| `response` | Object, nullable | Stored response, only with `Data,ChatResponse`. |

Nullable fields may be absent, and include values do not recover content that was never recorded. Configuration, message, and response objects retain the recorded JSON shape; they are not a fixed set of effective model defaults. The API returns stored objects, while the Backoffice request-details dialog displays a selected projection of them. Do not assume the UI's field filtering also applies to direct API retrieval.

## Retrieve aggregate AI usage

```http
GET /v1/platform/usage
```

Returns one aggregate object for the selected scope, rather than a list of log records. Totals, daily chat series, rankings, tools, and user options share a consistent view of stored data. Later writes or backfills appear on a subsequent request.

Chat totals include recorded failed requests unless an error filter excludes them. Additional ingestion, file-search, and embedding counts are returned separately. The endpoint does not return prompts, responses, configuration, or other log payloads. Use the log endpoints with explicit includes to retrieve individual records.

### Usage filters

<Accordion title="Endpoint parameters">
All query parameters are optional. This endpoint has no pagination, `include`, event/action, organization, or project filters.

| Parameter | Type | Default / notes |
| --- | --- | --- |
| `start_date` | Integer | Epoch milliseconds. Defaults to 30 days before the effective `end_date`. |
| `end_date` | Integer | Epoch milliseconds. Defaults to the current time. |
| `gateway_id` | String list | Gateway IDs; omitted means all gateways. The alias `gatewayId` is accepted. |
| `token_id` | String list | API token IDs and/or `none`. The alias `tokenId` is accepted. |
| `account_id` | String list | Account IDs and/or `none`. The alias `accountId` is accepted. |
| `has_error` | Boolean | Strict `true` or `false`; omitted includes both outcomes. |
</Accordion>

The ID lists use the same comma/repeated-parameter, deduplication, 100-selection, and `none` rules as log lists. IDs must have the correct node type. The legacy `status=success|error` alias is also accepted.

The date window must be increasing, nonnegative, and no longer than 90 days. Dates must be integer epoch milliseconds, with `end_date` at most `253402300799999`. Invalid dates, IDs, boolean values, or empty token/account selections return `400`. A record is in scope only when its start is at or after `start_date` and its end is at or before `end_date`.

```bash
curl "https://{BASE_URL}/v1/platform/usage?gateway_id={GATEWAY_ID}&token_id={TOKEN_ID},none&start_date=1767225600000&end_date=1769817600000&has_error=false" \
  -H "Authorization: Bearer {API_TOKEN}"
```

### Usage response schema

All counts and token totals are integers. All array sections are present, including `[]` when empty. Nullable values are omitted when unavailable.

| Field | Type | Notes |
| --- | --- | --- |
| `totals` | Object | Chat summary described below. |
| `daily` | Object array | Daily chat summary; ascending UTC dates with recorded activity. |
| `users` | Object array | At most 100 account groups, ranked by total tokens. |
| `users_by_requests` | Object array | At most 100 account groups, ranked by request count. |
| `keys` | Object array | At most 100 key groups, ranked by total tokens. |
| `tools` | Object array | Recorded tool calls, descending by calls then tool name. |
| `ancillary_daily` | Object array | Daily ingestion, file-search, and embedding counts. |
| `user_options` | Object array | At most 1,000 recorded account options matching the other filters; the selected `account_id` filter is intentionally ignored here. |
| `start_date`, `end_date` | Integer | Effective query boundaries in epoch milliseconds. |
| `rank_limit` | Integer | `100`. |
| `users_truncated`, `users_by_requests_truncated`, `keys_truncated`, `user_options_truncated` | Boolean | Whether the corresponding array has more matching groups than were returned. |

<Accordion title="Totals and daily fields">
| Field | Type | Notes |
| --- | --- | --- |
| `requests` | Integer | Recorded chat requests, including failures. |
| `requests_without_recorded_error` | Integer | Requests with no recorded error; does not establish response quality. |
| `input_tokens`, `output_tokens` | Integer | Sums of available recorded token values. Missing output tokens add zero. |
| `output_tokens_known_requests` | Integer | Requests with recorded output tokens. Present in `totals` only. |
| `attributed_users` | Integer | Distinct non-null account IDs. Daily values are not additive across days. |
| `average_response_latency`, `average_response_ttf` | Number, nullable | Average seconds over records that have the corresponding timing. |
| `date` | String | `YYYY-MM-DD` in UTC. Present in `daily` only. |
</Accordion>

<Accordion title="Rankings, tools, user options, and daily operations">
| Array | Entry fields |
| --- | --- |
| `users`, `users_by_requests` | Nullable strings `account_id`, `account_email`; integer `requests`, `input_tokens`, `output_tokens`. An absent account ID represents unattributed usage. |
| `keys` | Nullable string `token_id`; integer `requests`, `input_tokens`, `output_tokens`. An absent key ID represents usage without a recorded key. |
| `tools` | String `name`; integer `calls`. Repeated recorded tool calls count separately. |
| `user_options` | Nullable strings `account_id`, `account_email`, taken from matching historical logs rather than the current account directory. |
| `ancillary_daily` | String `date` (`YYYY-MM-DD`, UTC); integer `files_ingested`, `file_searches`, `embeddings`. |
</Accordion>

Rankings are capped independently; their truncation does not reduce totals. Tool counts have no ranking cap and do not prove successful execution. Ingestion counts deduplicate recorded artifact IDs per day, falling back to ingest/log IDs; file-search counts come from recorded search tool calls; embedding counts come from embedding events. Daily series omit dates without matching records rather than filling them with zeroes.

## Errors and limitations

| Case | Result |
| --- | --- |
| Missing or invalid authentication | Request is rejected by authentication middleware. |
| Authenticated account without at least the `operator` role | Request is rejected by the permission check. |
| Invalid node ID or pagination combination | Request is rejected before logs are returned. |
| Usage window over 90 days, invalid Usage date/error filters, or empty token/account selections | `400`. |
| Invalid detail ID/include, or a retained log that does not exist | `400` for an invalid detail query; `404` when the valid ID is not found. |
| Internal storage disabled | New logs are not persisted to Zylon log storage. Manual retrieval returns only already stored records. |
| Per-record modification or deletion | Not supported by the documented Logging API. Stored log retention is controlled by cleanup configuration. |

## Export chain of custody

When using these endpoints for a manual export, preserve evidence outside the response body:

- operator account or token identity;
- request timestamp, source IP, and request ID when available;
- exact URL filters, pagination values, and `include` values;
- number of records exported;
- incident, ticket, or legal hold reference.

Log retrieval calls are also logged as Backoffice actions: `/v1/platform/gateway/{gatewayId}/logs` emits `backoffice.gateway_logs.read`, and `/v1/platform/logs` and `/v1/platform/logs/{logId}` emit `backoffice.logs.read`. Preserve those events together with the exported response when a review, incident, or legal hold requires evidence of who accessed log records.
