Edit the provider in **Settings → Models** and open its **Customized settings**. These values tell the app what the model supports; they do not increase its actual capacity.

| Option | What to enter |
| --- | --- |
| Model ID | Exact API identifier accepted by the endpoint. |
| Display name | A recognizable label for the picker. |
| Context window | The model’s supported token capacity for a request. |
| Max output tokens | The maximum number of tokens the model can generate in one request. |
| Request output limit | The default number of output tokens reserved for an ordinary request, up to the model's output capacity. |
| Input types | Text and/or image only when the model supports them. |

## Capacity and request budget

Models measure text in **tokens**, which can be words, parts of words or punctuation. Token counts are not the same as word counts.

For example, a deployment may support a 131,072-token context and 32,768 output tokens while reserving 8,192 for an ordinary reply. Enter the server-supported capacities and choose a request limit no larger than its output capacity. These example numbers are not performance recommendations.

Newly discovered Zylon models default to a request limit of 8,192 tokens, or their lower advertised output capacity. Refreshing preserves settings for existing models, including models added manually. It does not replace their limits with the latest values from the server. Review existing models after a server change.

A large output reservation leaves less room for input. The summary used for [compaction](/zylon-code/everyday-use/long-conversations) has a separate budget; reducing the normal reply limit does not automatically reduce that summary limit. Ask your administrator to align compaction with a small model's capacity.

## Images

Expand the model's options and select **Image** if supported. At least one input type must remain selected. New custom models without inherited image capability begin as text-only. Screenshot-based tools need an image-capable model; the server must also support sending those images.

## Reasoning capabilities

Reasoning controls come from the selected model's advertised capabilities. Zylon models that report support offer **Off** and their supported effort levels in the composer. Use **Refresh models** to add newly available models. Refreshing also preserves saved reasoning settings; ask your administrator to update an existing model's settings when its capabilities change. Without configured reasoning capabilities, the Effort control is absent.

Use [Choose a model](/zylon-code/models/choosing-a-model) for the steps to enable, disable or change effort. Selecting another model applies that model's default. Editing a model's configured default does not replace an effort already selected in a conversation. **Default**, when offered, sends no explicit reasoning choice for Zylon.

The model service may use a different level when it cannot honor the requested setting. For example, Off may become a low level or Max may become High. Ask your administrator how your deployment handles these choices if the difference matters to your task.

## Defaults and errors

Restoring a provider's default catalog can remove your saved model settings; review the form before resetting it. A wrong model ID or protocol can save successfully and still fail when you send a request.

For advanced options such as headers, request compatibility, retries and timeouts, use [Profiles and YAML](/zylon-code/advanced/profiles-and-yaml) and the settings supported by your installation. Keep keys in credential fields, not directly in YAML.
