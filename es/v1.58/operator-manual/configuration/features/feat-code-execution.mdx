---
title: "Ejecución de código"
description: "Permite que el asistente ejecute código y trabaje con archivos en sandboxes aislados."
---

<Note>**Característica en Beta**</Note>

La ejecución de código permite al asistente ejecutar comandos bash y crear, editar y presentar archivos dentro de un sandbox aislado. Cada hilo de chat (o `container` de la API) tiene su propio sandbox, que crea bajo demanda el servicio OpenSandbox incluido en el mismo clúster de Kubernetes.

Los usuarios la ven en el Workspace cuando trabajan con Skills o generan archivos. Los desarrolladores pueden usarla a través de la API; ver [Herramienta de ejecución de código](/es/v1.58/developer-manual/build-with-zylon/tools/built-in/code-execution-tool).

La ejecución de código está **habilitada por defecto en los despliegues estándar de Zylon 1.58**. Los operadores pueden controlar su disponibilidad en el chat del Workspace con la siguiente configuración.

### Configuración

| Clave | Por defecto | Valores | Descripción |
|-----|---------|--------|-------------|
| `features.codeExecution.enabled` | `true` | `true \| false` | Permite las herramientas de ejecución de código en el chat del Workspace; consulta [Cuando está desactivada](#cuando-está-desactivada) para las limitaciones de la API |
| `features.codeExecution.timeout` | `60` | segundos | Tiempo de espera por defecto para cada comando que se ejecuta en el sandbox |
| `external.opensandbox.sessionTTLSeconds` | `600` | segundos | Tiempo que un sandbox inactivo se mantiene en ejecución antes de apagarse. Los archivos se conservan; la siguiente solicitud arranca un sandbox nuevo con los mismos archivos. |

### Ejemplo

```yaml
features:
    codeExecution:
        enabled: true
        timeout: 60
```

Para desactivar las herramientas de ejecución de código en el chat del Workspace:

```yaml
features:
    codeExecution:
        enabled: false
```

### Cuando está desactivada

Después de configurar `features.codeExecution.enabled: false`, ejecuta `sudo zylon-cli sync` para aplicar el cambio. El chat del Workspace elimina las herramientas de ejecución de código antes de enviar las solicitudes al modelo, incluso cuando una Skill las añadiría. El chat normal y las demás herramientas disponibles siguen funcionando; los pasos de una Skill que requieren ejecutar código no pueden ejecutarse a través de ese flujo de chat.

<Warning>
En Zylon 1.58, este flag **no desactiva globalmente la ejecución de código a través de la API de ZylonGPT** ni elimina el servicio OpenSandbox. El proveedor de GPT se configura por separado y usa OpenSandbox por defecto. Este flag controla el Workspace; la ejecución de código por API puede seguir disponible.
</Warning>

### Cómo funciona

- **Un sandbox por hilo.** Cada sandbox es un pod en el namespace `opensandbox-runtimes`, que se crea cuando el asistente ejecuta código por primera vez en un hilo y se apaga tras `sessionTTLSeconds` de inactividad.
- **Archivos persistentes.** Los archivos subidos, las salidas y los archivos del espacio de trabajo se almacenan en el bucket `sessions` del almacenamiento de objetos de la plataforma, por lo que sobreviven a los reinicios del sandbox y a las actualizaciones de la plataforma.
- **Imágenes descargadas previamente.** Las imágenes del sandbox se descargan durante la instalación y la actualización, así que no se necesita acceso al registro cuando arranca un sandbox. Esto también funciona en instalaciones airgapped.

### Acceso a la red

Los sandboxes no tienen acceso a internet. Por defecto, un sandbox de ejecución de código solo puede acceder a:

- DNS.
- La API de Zylon, para que el código del sandbox pueda llamar al modelo con los permisos del usuario que envió la solicitud.

Para que los sandboxes puedan acceder a otros servicios dentro del clúster, como una base de datos o una API internas, añádelos a `external.opensandbox.codeExecution.internal.services`. Cada entrada selecciona pods por sus etiquetas: `namespaceSelector` recibe las etiquetas del namespace y `podSelector` las de los pods. Escribe las etiquetas directamente, sin `matchLabels` (Zylon lo añade), y da al menos una etiqueta a cada selector: uno vacío permitiría a los sandboxes acceder a cualquier pod del clúster.

```yaml
external:
    opensandbox:
        codeExecution:
            internal:
                services:
                    - namespaceSelector:
                          kubernetes.io/metadata.name: analytics
                      podSelector:
                          app: postgres
```

<Warning>
El código del sandbox lo escribe el modelo de IA. Permite únicamente servicios que no te importe exponer a cualquier usuario que pueda chatear con el asistente.
</Warning>

### Recursos

Por defecto, los sandboxes no tienen límites de CPU ni de memoria. Para limitar el total de recursos que pueden usar los sandboxes, habilita la cuota y el rango de límites para el namespace de los sandboxes:

```yaml
opensandbox:
    runtime:
        resourceQuota:
            enabled: true    # Total para todos los sandboxes: 50 pods, 20 CPU, 40Gi de memoria (límites)
        limitRange:
            enabled: true    # Por sandbox: 1 CPU, 512Mi de memoria por defecto
```

### Imágenes del sandbox

| Clave | Por defecto |
|-----|---------|
| `external.opensandbox.codeExecution.image.repository` | `zylon-sandbox-templates/code-execution` |
| `external.opensandbox.codeExecution.image.tag` | `1.1.0` |

La imagen incluye Python 3 con las librerías de datos más habituales (pandas, numpy, matplotlib, openpyxl, python-docx, pypdf, entre otras) y herramientas de línea de comandos como `unzip`, `rg` y `sqlite3`.

### Enlaces a aplicaciones del sandbox

Cuando el asistente arranca una aplicación web o un servidor HTTP dentro del sandbox, como un panel o un gráfico interactivo, puede compartir un enlace a ella en el chat. Estos enlaces se sirven desde un subdominio dedicado de tu dominio de Zylon:

```
https://sandbox-exec.<tu_dominio_zylon>/<id-del-sandbox>/<puerto>/
```

El enlace se abre directamente en el navegador del usuario, así que el subdominio necesita un registro DNS y, con certificados manuales, su propio certificado SSL. Consulta [Subdominios](/es/v1.58/operator-manual/configuration/network/ports-and-dns#subdominios).

Un enlace solo funciona mientras su sandbox está en marcha. Cuando el sandbox se apaga tras `sessionTTLSeconds` de inactividad, la aplicación se detiene y el enlace deja de abrirse; el siguiente mensaje del usuario arranca un sandbox nuevo, y el asistente comparte un enlace nuevo si vuelve a arrancar la aplicación. El tráfico del navegador hacia el enlace no cuenta como actividad.

Los enlaces a aplicaciones del sandbox están desactivados por defecto.

#### Activar los enlaces a aplicaciones del sandbox

Después de configurar el subdominio, añade lo siguiente a `/etc/zylon/zylon-conf.yaml` y ejecuta `sudo zylon-cli sync`:

```yaml
features:
    codeExecution:
        tools:
            presentServer: true
```

#### Desactivar los enlaces a aplicaciones del sandbox

Para que el asistente deje de compartir enlaces a aplicaciones que se ejecutan en el sandbox, vuelve a poner `presentServer` en `false` (el valor por defecto) y ejecuta `sudo zylon-cli sync`. El asistente puede seguir ejecutando código y presentando archivos.

```yaml
features:
    codeExecution:
        tools:
            presentServer: false
```

<Note>
Esta opción solo controla si el asistente comparte enlaces. El ingress `sandbox-exec` forma parte del gateway del sandbox y sigue desplegado.
</Note>

### Resolución de problemas

Comprueba los sandboxes que están en ejecución:

```bash
sudo kubectl get pods -n opensandbox-runtimes
```

Revisa los logs del servidor de OpenSandbox:

```bash
sudo kubectl logs -n opensandbox deploy/opensandbox-server --tail=200
```

Si la ejecución de código no está disponible en el chat del Workspace, comprueba `features.codeExecution.enabled` y ejecuta `sudo zylon-cli sync` después de cambiarlo.

Si un enlace a una aplicación del sandbox no carga o muestra un aviso de certificado, comprueba el [registro DNS](/es/v1.58/operator-manual/configuration/network/ports-and-dns#subdominios) de `sandbox-exec.<tu_dominio_zylon>` y, con certificados manuales, el [secret `zylon-tls-sandbox-exec`](/es/v1.58/operator-manual/configuration/network/ports-and-dns#certificados-ssl-para-subdominios) del namespace `opensandbox`. Para ver el host y el secret que espera el ingress del sandbox, ejecuta lo siguiente y revisa la línea `TLS` (`zylon-tls-sandbox-exec terminates sandbox-exec.<tu_dominio_zylon>`):

```bash
sudo kubectl describe ingress opensandbox-ingress-gateway -n opensandbox
```

El error `code_execution provider is not configured.` significa que falta el proveedor de ejecución de código de GPT. Comprueba la configuración del proveedor de GPT y el servicio OpenSandbox; este error no es el resultado esperado de desactivar únicamente el flag del Workspace.
